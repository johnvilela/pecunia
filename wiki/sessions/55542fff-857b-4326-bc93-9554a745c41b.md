### Gap #1 explained, then fixed as balance adjustments

Asked to explain gap #1 in detail first: `Account.Balance` is a stored column written directly by `kakei ac edit`, with nothing recording an adjustment, logging the old value, or detecting drift — the one number in kakei that could silently disagree with the transactions meant to explain it.

Three fix options were presented before any code:
- **A — edits become adjustment transactions.** Small diff, the ledger explains every move by construction, but doesn't detect drift caused by a future bug.
- **B — store an opening balance + `kakei ac reconcile`.** Detects any drift including from future bugs, but doesn't stop new drift from being created by hand; least UX change.
- **C — compute the balance from the ledger, store nothing** (the goals/budgets answer). Architecturally pure but the biggest diff by far, and destabilizes the card over-limit check, which reads the stored balance mid-transaction.

Recommendation given: A now, B as a cheap follow-up, C not worth 5x the diff. User: "Lets follow with option A and a thrid kind that can't be selected by the user manually." Built exactly that — full design and implementation in [[decisions/0015-balance-adjustments-as-a-hidden-kind]]. The exploration flagged, and the build confirmed, that SQLite's inability to `ALTER` a `CHECK` makes this the repo's first full table rebuild, and that `PRAGMA foreign_keys` is a no-op inside a transaction — the migration runner had to grow an explicit OFF / `foreign_key_check` / ON wrapper around the migration batch, or dropping the old `transactions` table would have cascade-wiped every tag.

### Gap #2 explained, then fixed as write-time bill refresh

Asked directly: "How do you suggest to fix the gap #2?" (read paths still write). Diagnosis: `bills.Ensure`/`refreshOpen` ran their UPDATE unconditionally on every open bill on every read, because writes only ever kept *payments* fresh — a card *charge* never touched its bill's total, so reads had to catch up. Proposed and built the two-step fix in [[decisions/0016-bill-reads-stop-writing]]: reads write only when the computed total/status actually differs from the stored row, and a charge now refreshes its own bill's total inside the same write transaction that recorded it (mirroring how a payment already refreshes its bill). The rule holding it together, caught by the exploration before it could become a bug: a charge must never *create* a bill row at write time — installments reach up to 59 months out, and a future bill row would break `bills.Open`'s "newest open bill is the current one" assumption.

### Verification

Both fixes landed as commits in the plan's phase order, TDD per [[rules/tdd]], full suite green after each, `gofmt`/`go vet` clean. The balance-adjustment migration was verified by migrating the populated dev database **in place** (no reseed) — 47 transactions and 49 tags unchanged, `foreign_key_check` empty. The bill-refresh fix was verified by running `kakei s`, `kakei cc bill`, `kakei bg` back-to-back and diffing `card_bills.updated_at` snapshots to confirm byte-for-byte no writes on a clean read. A drive-by fix also landed: `test: survive being run late in the month`, fixing two date-dependent tests that failed when run on Aug 27 (a bill-cycle assumption, and a seed fixture that could never render "upcoming" late in the month).
