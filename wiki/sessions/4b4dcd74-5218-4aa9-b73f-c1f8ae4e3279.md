### Goals module

User: "execute the task @wiki/tasks/06-goals-module.md - ask me anything to refine this. Use caveman skills." Three parallel Explore agents (module package layout, `cmd`/db-migration conventions, the `transactions`/currency surface) plus a Plan agent produced a full implementation plan before any code — six design questions settled, all written up in [[decisions/0010-goal-progress-summed-from-the-ledger]]:

- No `current_value` column — progress is summed from linked transactions on every read.
- The kind (saving/paying) flips the progress sign in Go, not SQL.
- A goal carries its own currency; only same-currency transactions may link, enforced at three layers (form options, a store-side `fillGoalCurrency` that reads both currencies back before validating, and `Transaction.Validate`).
- Goals are id-only, no code, no colour — following transactions rather than every other module.
- Deleting a goal is never refused (`ON DELETE SET NULL`); the confirmation counts affected transactions instead.
- Field is `Name` not the spec's `Title`, reusing `core.ValidateName` — one of two deliberate deviations from the approved plan (the other being the store-side currency fill instead of a separate join, since a transaction's `Currency` is empty on the write path and only filled by read joins).

Built via TDD per [[rules/tdd]], phase by phase: schema (`007_goals.sql`, `goal_id` added to `transactions` via `ALTER TABLE`), pure model (`internal/goals/goal.go` — `Progress()`, `Remaining()`, `Reached()`, `Verb()`, `Validate()`), store (`internal/goals/store.go` — one correlated-subquery `SELECT`, no join+`GROUP BY`, so `Get` on a missing id still returns zero rows), UI (`internal/goals/ui.go` — label, bar, table, bordered detail card coloured by state), `cmd/goals.go` + two lines in `cmd/main.go`, then threading the optional link through `internal/transactions/{transaction,store,ui}.go` and `cmd/transactions.go` (`--goal ID` filter, `narrowed=true` so it doesn't get clipped by the this-month default), and finally goal fixtures in `scripts/seed/main.go`.

`internal/goals` cannot import `internal/transactions` (the reverse import already exists), so its own tests link transactions with raw SQL — the same trick [[decisions/0009-bills-as-rows-and-installments-as-transactions]] used for `internal/bills`.

Verified live against the reseeded dev DB: editing a linked transaction from R$1200.00 to R$2000.00 moved `Notebook novo` from R$2100.00 to R$2900.00 with no write to the goals table at all — the point of computing rather than storing progress. Also checked a goal past its target (bar clamps full, wording flips to "past it"), the BTC goal's eight decimal places, `--goal` widening past the this-month default, and a deleted goal leaving its transactions with their money and no link.

Known holes carried into the decision page: `kakei cc pay` sets no goal, so a bill payment has to be edited afterward to feed a paying goal; `Progress()*100/Target` can overflow at an absurd BTC-satoshi scale, the same non-guard `cards.usagePct` already has; no goal column in `kakei t`'s list table (deliberate, pinned by `TestTableHasNoGoalColumn`).

`go test ./...`, `gofmt`, `go vet` clean throughout.

### Two view changes after the module landed

Both from the user looking at the real output, and both TDD'd like the rest:

- A green `✓` after the name once a goal is reached, through a `name(g)` helper rather than inline in the table, so the picker and the transaction form's goal select carry it too.
- **`kakei g` now lists one card per goal** — the bar is the point, and it does not fit in a table row. The compact table moved behind `kakei g --resume`. One string comparison in `runGoals`, not a `flag.FlagSet`: one boolean does not need the machinery `kakei t` has for ten flags. The `✓` was extended to the card at the same time, since the card is the default view now and the mark would otherwise have been reachable only behind the flag.
