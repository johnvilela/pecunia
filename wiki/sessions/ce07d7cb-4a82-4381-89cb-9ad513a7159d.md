## What happened

Built the credit-card module end-to-end via TDD, from the spec in [[tasks/02-credit-card-module]], across four rounds: explore+plan, implement, a bug found from a direct question about the dev DB, and a UI/UX correction from user screenshots.

### Explore + plan

User: "Execute the @wiki/tasks/02-credit-card-module.md - ask me anything to refine this. Use caveman and design skill. Use TDD." Two Explore agents read the whole repo (every source file, every test, all wiki pages) before a Plan agent produced four verdicts on the open questions in the spec:

1. **Dates → day-of-month INTEGER (1-31)**, not absolute `TEXT` dates — a card closes on the same day every month; clamp to month length only when something computes an actual date (deferred to the transactions module).
2. **`balance` = amount already used on the open invoice**; `Available()` is computed as `Limit - Balance`, matching the accounts module's "stored quantity, computed views" pattern.
3. **Extract a shared `internal/core` package** (Option A) rather than having `cards` import `accounts` directly (Option B, rejected as a domain-naming smell) or duplicating the money/validation code (Option C, rejected as forking a money path).
4. **No FK to an account** — the spec doesn't ask for one, and it's a one-line migration to add when the transactions module actually needs the link.

Full decision write-ups: [[decisions/0006-credit-card-money-schedule-and-over-limit-model]] (semantics) and [[decisions/0005-internal-core-shared-kernel]] (the refactor).

### Phase 0 — shared kernel refactor

Extracted `internal/core` from `internal/accounts`: currencies, the 12-color palette, code generation/validation, `ParseAmount`/`FormatAmount`, `Confirm`, and a new generic `Pick[T any]`. `accounts` was rewired onto it with zero behavior change — the existing 158+ subtests were the only regression test needed. Two dead identifiers (`labelStyle`, `styledCode` in `ui.go`) deleted along the way. Commit: `refactor: extract shared currency, palette and picker helpers into internal/core`.

### TDD cycles — internal/cards + cc commands

Six red/green cycles, each with its own test file written first:
1. Schema — `internal/db/migrations/002_credit_cards.sql`. Along the way, `internal/db/db_test.go`'s `TestOpenMigratesOnceOnly` was changed from a hardcoded `n != 1` to deriving the expected count from the embedded migration files, so a future `003` wouldn't need a matching test edit (it would have, otherwise — this was the day's first red).
2. Model — `internal/cards/card.go`: `Card`, `Available()`, `Fmt()`, `ParseDay`, `NextDate`. A real bug caught here: the first `NextDate` used `AddDate(0,1,0)`, which overshoots on month-end (31 Aug → 1 Oct instead of 1 Sep); fixed with `time.Date(y, m+1, 1, …)`.
3. Store — `internal/cards/store.go`, transliterated from `accounts/store.go` minus freeze. Deliberately pinned the exact "Update on a missing id returns ErrNotFound" bug that accounts had shipped once already, on day one.
4. UI — `internal/cards/ui.go`: table, bordered detail card, usage bar.
5. Command — `cmd/cards.go`, wired into `cmd/main.go`'s dispatch as `credit-card`/`cc`.
6. Seed — six card fixtures added to `scripts/seed/main.go`, covering every render branch (over limit, zero balance, no description, all four currencies, day edges).

Commit: `feat: add credit card cli with sqlite storage and tui`.

### Bug: blank name via a pty's EOF stdin

User asked "Does the seed on dev db updated with cards?" — while checking, a card row turned up with no name (`[PXQ55]`). Root cause and fix: [[gotchas/huh-form-skips-validators-on-eof]]. Fixed in both `cards` and `accounts` stores (pre-existing bug, not introduced by this module). Commit: `fix: reject a blank name in the account and card stores`.

### UI/UX correction — used vs. available

User, from a screenshot: "The UI/UX showing the relation of limit and used is looking strange. A cc will never be positive, thus it will never be green. On the last cc card i don't know if i have 1550 avaliable to use or if the current used value it 1550." Full redesign details in [[decisions/0006-credit-card-money-schedule-and-over-limit-model]] — table header became `USED / LIMIT`, green removed entirely, red only once over the limit, and the detail card spells out "over the limit" instead of showing a negative "available". A follow-up question ("Why only ITAU1 is red?") confirmed the new rule was working as intended, not a bug — every other seeded card had comfortable room.

### Feature: over-limit allowance

User: "we need to add a flag on the cc table to tell that this card can be used above the limit. By default is will be set false." Added `over_limit_allowed` (migration `003`, default 0), enforced as a real constraint via `Card.ValidateBalance()` inside `Store.Create`/`Store.Update` — not just a UI toggle — which also blocks revoking the allowance while a card is currently over its limit. Marked in the table/details with an `↑`. This rule immediately caught real data: the seed fixture `ITAU1` (R$4120 used against a R$3000 limit) could not exist with the flag off, so it became `OverLimitAllowed: true` in the fixtures. Commit: `feat(cards): add an over-limit allowance that caps the balance when off`.

### Final commit

`/git-commit` → `docs(wiki): add memoria pages and the credit card task spec` — all code had already been committed as the session went; this one carried only the memoria pages (including some left untracked by an earlier session) and the working tree ended clean.
