## What happened

Two parts, both finished and committed together by the end: built an MCP server exposing all nine kakei modules to an AI agent, then built and finished installing that server into other AI agents' own configs.

### MCP server

User: "For now i think the CLI is strong may be useful. Lets create a MCP, this way we give an AI agent ways to check the user information and give insights and ask questions. Ask me anything to refine this request."

Extensive exploration first — every module's store signatures, `internal/logs`, the go-sdk's `mcp.AddTool`/`NewServer`/`Server.Run`/`StdioTransport`/`CallToolResult`/`ToolHandlerFor` via `go doc` — before `github.com/modelcontextprotocol/go-sdk` was added and `cmd/mcp.go` written, TDD per [[rules/tdd]] (`cmd/mcp_test.go` first).

Result: `kakei mcp` serves one tool per module (`kakei_accounts`, `kakei_credit_cards`, `kakei_transactions`, `kakei_categories`, `kakei_goals`, `kakei_recurring_bills`, `kakei_budgets`, `kakei_summary`, `kakei_logs`), each tool's `action` parameter mirroring the CLI's own verbs, routed through the same stores the CLI uses — so frozen accounts, card limits, currency freezes and write-time bill refreshes all still hold. `logs.Actor` is a new process-wide audit source (`kakei mcp` sets it to `ai` at startup, retiring the "nothing writes it yet" placeholder from [[decisions/0014-logs-as-a-single-audit-table]]); every store call site was renamed from a hardcoded `logs.User` to `logs.Actor`. Full design: [[decisions/0017-mcp-server-exposes-every-module-as-a-tool]].

Verified with the full test suite green, `gofmt`/`go vet` clean, and a live stdio smoke test: a real JSON-RPC `initialize` → `tools/list` → `tools/call` (create an account, then read the summary back showing it) → confirming the audit row's `source` was `ai` via `kakei logs --source ai`.

### MCP install

User, immediately after: "on the 'kakei mcp' does it install the MCP? If it doesnt: we may add a flag on the 'kakei setup' that install the MCP on the selected AI agent (codex, claude-code, opencode...). Ask me anything to refine this."

A plan was written first (`~/.claude/plans/on-the-kakei-mcp-iridescent-pine.md`, outside the repo), then `cmd/mcp_install_test.go` and `cmd/mcp_install.go`, with edits to `cmd/mcp.go`, `cmd/main.go` and `cmd/setup.go`. The installer ended up as `kakei mcp install <agent>` rather than a `kakei setup` flag, plus a prompt at the end of `kakei setup` offering to run it (silently skipped with no TTY). Agents with their own CLI (claude-code, codex, gemini, cursor) get shelled out to via their own `mcp add`; opencode, which has none, gets its `mcp` entry merged straight into `opencode.json` — preserving pre-existing keys, but refusing outright (with a paste-ready snippet instead) when the file is JSONC with comments it can't safely re-serialize. What gets registered is the absolute path of the running binary, so a dev build's install points an agent at the isolated `dev` binary and `kakei.dev.db` ([[decisions/0004-dev-build-isolated-by-ldflags]]).

Live-verified: `kakei mcp install claude-code` and `kakei mcp install codex` both produced a connected entry in that agent's own `mcp list` — a real handshake, not just a config write. Both were removed afterward since they pointed at a scratch build. `go test`/`gofmt`/`go vet` clean throughout. Full design: [[decisions/0018-mcp-install-writes-agent-config-files]].
