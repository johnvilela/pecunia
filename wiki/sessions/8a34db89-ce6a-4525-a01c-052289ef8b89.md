## What happened

Two features, each explored, planned, built and shipped via its own PR in one session: locking `master` to PR-only with CI and a release-on-merge pipeline, then a `kakei upgrade` self-update command.

### PR-only master, CI checks, release on merge

User: "Lets block the 'master' branch to commits. All commits there must come from PR. Also we must setup github actions to execute when a PR is created to check the code and run the test suite. And another github actions to execute when we merge the PR, it will create a new github release using the version of the CLI." Two Explore agents mapped the repo (layout, version state, tests, CI, GitHub remote/branch) before any code — the repo had no `.github/`, no version, no tags at all.

Built: `var version = "0.1.0"` in `cmd/main.go` (new `kakei version`/`-v`/`--version`, also reused by the MCP server identity in `cmd/mcp.go`, replacing its hardcoded drifting `"1.0.0"`), `.github/workflows/ci.yml` (gofmt/vet/build/test on every PR to master) and `.github/workflows/release.yml` (greps the version on push to master, skips if the tag already exists, else cross-compiles 4 tarballs and creates a GitHub release). Committed straight to master (`ci: add pr checks, release-on-merge workflow, and cli version`) since the ruleset didn't exist yet, then a repo ruleset was created via `gh api` (PR required, 0 approvals, required status check `checks`, no admin bypass, no deletion/force-push).

Verified live end to end: `kakei version` prints `0.1.0`; the first release run produced v0.1.0 with all 4 tarballs, one downloaded and confirmed to run; a probe direct push to master was rejected ("Changes must be made through a pull request"). The wiki write-up (decision 0019) was landed through the new process itself as PR #1 (`docs/wiki-0019`) — CI caught a real bug in the first workflow version (`go build ./cmd` collides with the `cmd` directory name on a clean checkout, fixed with `-o /dev/null`), then went green, squash-merged, and the post-merge release run correctly skipped re-releasing v0.1.0. One flake noted: a single `go test ./...` failure in `kakei/cmd` that never reproduced across 6 re-runs.

Full design: [[decisions/0019-pr-only-master-with-ci-and-release-on-merge]].

### kakei upgrade

User, on a new branch: "lets create a command called 'kakei upgrade'. It will check if there is a new version, if so it will show the changelog and ask the user if he wants to update the CLI. After updating, it will run the migrations to update the database. There should be a flag '-y' run without asking anything, just showing the changelog." Two Explore agents first confirmed migrations already auto-apply on every `db.Open()` (so "run migrations" only needs the *new* binary to run once), that there was no HTTP client or no-TTY detection anywhere in the repo, and the exact release asset naming from the just-built release workflow.

Built TDD, stdlib only: `cmd/upgrade.go` fetches the GitHub releases list, does real numeric semver comparison (`versionLess`) so a dev build ahead of the latest release never reads as needing a downgrade, prints the changelog of every release between current and latest, confirms via `core.Confirm` (which gained an affirmative-label parameter — it hardcoded "Yes, delete", now also "Yes, upgrade" and "Yes, install"), downloads and extracts the platform tarball, rename-swaps the running binary (temp file same-dir, `filepath.EvalSymlinks`, sudo hint on permission errors), then execs the new binary's new `kakei migrate` command. `-y` skips only the confirmation, never the changelog.

A live test against the real GitHub API caught a real edge: a fake 0.0.1 build upgrading to the real v0.1.0 (which predates `migrate`) had its exec fail and sink the whole command — fixed so a failed migrate exec is a soft failure ("they will apply on the next kakei run"), since `db.Open()` migrates on every run anyway. Version bumped to 0.2.0 in the same PR, so merging it releases the feature automatically. Shipped as PR #2 (`feat/upgrade`), CI green, left open and unmerged for review at session end.
