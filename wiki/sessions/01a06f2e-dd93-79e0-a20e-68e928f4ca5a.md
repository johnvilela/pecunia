## What happened

User asked how to access Pecunia's SQLite database from the current PC when the canonical database will live on the old PC running Omni (per [[decisions/0023-pecunia-is-an-omni-plugin]], Omni launches Pecunia on its host). Explicit ask: "Do no change anything yet, lets just discuss ideas" — this was a discussion-only session, no code was touched.

### Exploration

Before answering, the assistant read `wiki/index.md`, grepped the repo for existing database/sync/remote/omni references, and inspected `internal/db/db.go`, `cmd/mcp.go`, `cmd/omni.go`, and the relevant wiki decisions ([[decisions/0013-data-integrity-fixes-and-known-gaps]], [[decisions/0016-bill-reads-stop-writing]], [[decisions/0017-mcp-server-exposes-every-module-as-a-tool]], [[decisions/0023-pecunia-is-an-omni-plugin]], [[decisions/0024-pecunia-coach-and-omni-prompt-commands]]) to confirm what already exists (WAL mode with `-wal`/`-shm` sidecars, the stdio MCP server, the Omni plugin manifest) before recommending anything.

### Recommendation

Keep the old PC as the single authoritative SQLite owner and bring execution to the data rather than synchronizing the database file:

- Reach the old PC over SSH, running either the plain CLI (`ssh -t finance-pc pecunia summary`) or the MCP server over stdio (`ssh finance-pc pecunia mcp`, no `-t`, since stdout is the MCP protocol channel).
- Put SSH behind a private overlay network — Tailscale or WireGuard — rather than exposing SSH or a Pecunia service to the public internet. Tailscale was named as the candidate to evaluate later; the user said they'd learn more about it later, and nothing was set up.
- Explicitly avoid pointing `PECUNIA_DB` at SSHFS/NFS/SMB/Syncthing/Dropbox or any other live network-mounted or synchronized copy — Pecunia's WAL mode, `-wal`/`-shm` sidecars, locking and busy timeout depend on local-filesystem semantics that network filesystems and independent sync can violate.
- Flagged a safety gap for later: the current MCP server exposes writes as well as reads, so a read-only PC would benefit from a future `pecunia mcp --read-only` mode rather than relying on prompt instructions.
- Named further options as worth building only later: a first-class `pecunia serve` HTTP/Streamable-MCP service if multiple clients appear, a one-way consistent snapshot (SQLite Online Backup API / `VACUUM INTO`) for offline reads, Litestream or periodic snapshots for backup (a separate concern from remote access), and a client/server database (Postgres) only if Pecunia ever becomes multi-user.
